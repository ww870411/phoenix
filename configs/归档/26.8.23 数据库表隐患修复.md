## 一、审计背景与核心结论

### 1.1 触发背景
在页面 `/projects/monthly_data_show/import-workspace` 执行 CSV 导入更新（覆盖已存在的存量月报记录）时，后端接口抛出数据库异常：
```text
(psycopg2.errors.InvalidColumnReference) there is no unique or exclusion constraint matching the ON CONFLICT specification
[SQL: INSERT INTO monthly_data_show (...) VALUES (...) ON CONFLICT (company, item, date, period, type) DO UPDATE SET ...]
```
经排查，该报错由物理表缺失复合唯一索引（`UNIQUE INDEX`）引发。为彻底防范全系统各业务模块潜在的数据写入与并发冲突风险，技术团队对全库 21 张物理业务表展开了全面的 5 维健康体检（主键约束、自增序列对齐、ID重号、唯一索引覆盖、NULL违规）。

### 1.2 核心结论
- **核心数据资产安全**：9.6 万行的日报基础表 `daily_basic_data`、气温表 `temperature_data`、煤炭表 `coal_inventory_data`、直管/管件发货表等核心数据完全健康，无任何数据损坏或丢失；
- **排查出的隐患性质**：主要集中在历史表重命名、快速建表或迁移时，遗漏了“物理主键约束”、“自增序列绑定与计数器对齐”以及“业务唯一索引”；
- **修复状态**：通过事务级原子自愈脚本执行，全库 21 张表已全部完成修复并固化到系统脚本库。

## 二、排查出的 3 大类结构隐患

### 🚨 隐患 1：自增序列严重滞后（Sequence Lagging，最高危）
- **现象与风险**：物理表中存量数据的 `MAX(id)` 已经很大（如 4564），但 PostgreSQL 自增序列（Sequence）计数器还停留在较小数值（如 55）。当业务系统下一次执行常规 `INSERT`（不传 `id` 依赖自增）时，Postgres 会生成 56、57... 从而与存量数据发生物理主键碰撞（`duplicate key value violates unique constraint`），直接阻断用户填报与发货。
- **涉及表**：
  1. `tube.tube_fitting_baseline`：表内最大 ID 为 **4564**，序列计数仅为 **55**（滞后 4509）；
  2. `tube.tube_pipe_baseline`：表内最大 ID 为 **802**，序列计数仅为 **29**（滞后 773）；
  3. `tube.tube_weather_hourly`：表内最大 ID 为 **5904**，序列计数仅为 **1**；
  4. `tube.tube_weather_daily`：表内最大 ID 为 **246**，序列计数仅为 **1**；
  5. `tube.tube_gis`：表内最大 ID 为 **59**，序列计数仅为 **1**；
  6. `tube.tube_daily_usage`：表内最大 ID 为 **80**，序列计数仅为 **1**。

### ⚠️ 隐患 2：物理表缺失主键约束（Missing Primary Key）
- **现象与风险**：表中包含 `id` 或 `token` 字段，但在建表 DDL 中遗漏了 `PRIMARY KEY` 约束，数据库无法在底层引擎级别强制保证单行记录唯一性，且无法被 ORM 变更追踪或外键引用。
- **涉及表**：
  1. `public.auth_sessions`：以 `token` 为凭证但未设置物理主键；
  2. `public.paln_and_real_month_data`：历史计划实际数据表，未设物理主键与自增序列；
  3. `tube.tube_daily_plan`、`tube.tube_daily_usage`、`tube.tube_gis`、`tube.tube_weather_daily`、`tube.tube_weather_hourly`、`tube.tube_inventory_adjustment` 等。

### ⚠️ 隐患 3：历史无主键期间产生的局部 ID 重号
- **现象与风险**：过去在没有物理主键约束保护且自增序列倒退/重复导入的情况下，表中存量数据产生了部分重复的 `id` 编号。
- **涉及表**：
  1. `logs.tube_operation_logs`（总行数 527，仅有 319 个独立 ID）；
  2. `tube.tube_daily_plan`（总行数 204，仅有 177 个独立 ID）。

### 脚本 2：针对 monthly_data_show 单表的专项修复脚本（自动 Schema 识别）
- **本地文件位置**：`backend/sql/fix_monthly_data_show_unique_index.sql`
- **功能特点**：自动探知 `monthly_data_show` 所在的具体物理 schema，创建 `(company, item, date, period, type)` 5 维复合唯一索引，彻底解决 CSV 覆盖导入时的 `ON CONFLICT` 异常。

```sql
DO $$
DECLARE
    v_schema text;
BEGIN
    -- 1. 动态获取 monthly_data_show 表所在的实际 schema
    SELECT table_schema INTO v_schema
    FROM information_schema.tables
    WHERE table_name = 'monthly_data_show'
    LIMIT 1;

    IF v_schema IS NULL THEN
        RAISE EXCEPTION '未在当前数据库中找到表 monthly_data_show，请检查连接！';
    END IF;

    -- 2. 在同 schema 下创建序列并绑定
    EXECUTE format('CREATE SEQUENCE IF NOT EXISTS %I.monthly_data_show_id_seq;', v_schema);
    EXECUTE format('SELECT setval(''%I.monthly_data_show_id_seq'', COALESCE((SELECT MAX(id) FROM %I.monthly_data_show), 0) + 1, false);', v_schema, v_schema);
    EXECUTE format('ALTER TABLE %I.monthly_data_show ALTER COLUMN id SET DEFAULT nextval(''%I.monthly_data_show_id_seq'');', v_schema, v_schema);
    EXECUTE format('ALTER SEQUENCE %I.monthly_data_show_id_seq OWNED BY %I.monthly_data_show.id;', v_schema, v_schema);

    -- 3. 补齐主键约束（若尚无）
    IF NOT EXISTS (
        SELECT 1 FROM pg_constraint c
        JOIN pg_class t ON c.conrelid = t.oid
        JOIN pg_namespace n ON t.relnamespace = n.oid
```
