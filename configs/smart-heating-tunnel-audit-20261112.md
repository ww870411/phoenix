# 智慧供热中继页面功能与性能检查

后续实施：用户已授权直接优化。本报告保留检查时证据，当前实现、14 项后端回归结果、前端验证及部署/回滚说明见 `configs/progress.md` 中“智慧供热中继连接复用与重复回源优化”。此前“只读排查”的描述仅指检查阶段；线上与真实 Win7 的效果尚未复测。

检查日期：2026-11-12（香港时区）。范围：本地页面、仓库源码、本地 Docker 服务，以及线上公开静态资源。用户确认：慢的是内网页面，中继连接线上 `https://platform.smartview.top`。

## 结论与边界

存在可确认的功能问题和性能改进点。线上缓存命中仍有秒级耗时，不能把慢全部归因于中继或内网平台。尚未获得线上已认证的浏览器请求瀑布和办公电脑执行日志，因此不能确定线上动态页面的主要瓶颈，也未验证全部业务按钮、登录与操作提交。

本轮只读排查，新增本报告；未改业务代码、运行配置或线上服务。源码结论基于当前工作区；未核对线上部署的源码版本。没有执行会写入配置的既有隧道测试。

## 优化路径与验收

### 第一阶段：定位线上耗时并修正确定性问题

1. 记录同一请求的排队、办公电脑内网请求、回传、网关处理与总耗时；现有 duration_ms 只有内网执行时间，尚未用于网关分段展示。用轻量日志或 Server-Timing 即可，不引入额外观测平台。
2. 在实际浏览器冷缓存与热缓存各测一轮网络瀑布；记录 HTML、脚本、CSS、首个业务数据的耗时、缓存状态和重复请求。分别从当前电脑与办公电脑对线上地址采样，以区分公网连接和中继环节。
3. 修正密码留空、下载地址、配置覆盖提示及失效任务派发；对配置、下载、超时任务跳过做针对性回归。

验收：能按同一请求解释时间花在哪里；配置保存不误删密码；生成地址在办公电脑可达；超时请求不再占用后续通道。当前不承诺未经测量的提速比例。

### 第二阶段：减少首屏请求和重复传输

1. 按真实页面瀑布补齐必需的 JS/CSS/图片/字体缓存，再处理缓存版本与失效。不要把 CSS 的全部 143 个未缓存引用直接当成首屏必需文件。
2. 每份 HTML 都同步注入 jQuery 1.8.2，会阻塞 HTML 解析；若原页面已有 jQuery，还可能重复初始化插件。核对实际依赖顺序后去重或只对确有需要的页面注入，不直接改 async/defer 破坏老系统依赖。
3. 对并发重复的同一静态资源合并回源，避免多个窗口或 iframe 同时未命中时重复走中继。
4. 线上 gzip 已有；优先核实连接建立、网络路径和服务处理时间，再决定是否需要额外静态资源分发方案。

验收：记录首屏请求数、阻塞脚本数、缓存命中率、冷/热启动可操作时间；相同静态资源并发未命中只回源一次，版本改变能获取新资源。

### 第三阶段：优化中继传输

客户端每个 worker 按“poll → 内网请求 → respond → 下一次 poll”串行工作；当前使用 urllib，每次公网请求没有显式复用的连接池，回传又使用 Base64 JSON，增加约三分之一的正文体积，并完整读入内存。

先评估 Win7/Python 3.8 环境可用且维护范围明确的标准 HTTP 客户端库，实现线程隔离的持久连接与连接池。依据内网耗时和回传耗时判断是否拆分任务领取和执行；不盲目提高目前已为 16 的线程数。确认瓶颈仍在传输后，再评估复用长连接的协议及二进制传输；协议调整需考虑云端入口、断线恢复、在途任务与客户端迁移。

验收：在相同网络和请求集下比较公网建连次数、回传字节数、队列等待 p50/p95、端到端耗时和失败率，并回归登录、跳转、表单、静态资源与 JSON 数据。
